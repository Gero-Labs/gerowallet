## TL;DR

**Gero already has 70% of the scaffolding.** Onboarding network grid, BIP-39 mnemonic generation, PRF/PassKey encryption, `IChainAdapter` interface, `NetworkInfo` registry, per-wallet IndexedDB, store-broadcast pattern, Ably real-time, and Vuetify components are all reusable as-is.

**The 30% that's inherently different from Cardano/Bitcoin** is concentrated in five areas: (1) three address types per wallet (shielded/unshielded/dust) instead of one, (2) DUST as a non-transferable, time-decaying fee resource, (3) ZK proof generation that takes ~10s/tx and bloats the bundle by ~25 MB if WASM-bundled, (4) a separate-but-CIP-30-shaped DApp connector at `window.midnight[walletId]`, and (5) a Cardano-side DUST registration tx that only completes after a ~2.5 hour bridge relay.

**The `new-midnight-backup` prototype is connected-mock**: solid UI work and a correctly-architected `midnightStore`, but zero `@midnight-ntwrk/*` SDK code, fake encrypted keys in IndexedDB, and store changes that are mostly *reverts* of unrelated work that landed after the branch was cut. Cherry-pick the components and types onto current main; do not rebase.

## What's Inherently Different (these need explicit decisions, not just code)

### 1. Three address types per wallet
Cardano = one base + stake address. Bitcoin = one address per script type. **Midnight = three independent address types per account, each derived from a different role**:

| Type | Role | HRP example | Used for |
|---|---|---|---|
| Shielded | `Roles.Zswap` (3) | `mn_shield-addr_test...` | Private (ZK) tokens |
| Unshielded | `Roles.NightExternal` (0) | `mn_addr_preprod1...` | Public NIGHT/UTXOs |
| Dust | `Roles.Dust` (4) | `mn_dust-addr...` | DUST receiving / generation |

Receive UI must show all three (Lace shows three copy buttons). HD path is `m/44'/2400'/account'/role/index`.

### 2. DUST is non-transferable, time-decaying, capped
DUST is the fee token. **Users can't buy or transfer it.** It is generated by registering NIGHT UTXOs against a dust address; the rate decays toward a cap. From the partners guide:

```
night_dust_ratio = 5_000_000_000  // 5 DUST per NIGHT (initial)
generation_decay_rate = 8_267     // ≈ 1 week to reach cap
DUST(t) = max(0, min(C, r·g) - r·d)
```

This needs a **dust tank UI primitive** (Lace ships one) showing four states: `empty | refilling | filled | decaying`, with a time-remaining estimate. NIGHT becomes a regular token that *also* generates dust — Lace correctly displays **DUST as the native token, NIGHT as a designated unshielded token**.

### 3. ZK proof generation — three architectural options
Each transaction requires zk-SNARK generation that takes "tens of seconds":

| Option | UX | Bundle | Privacy | Notes |
|---|---|---|---|---|
| **External proof server** (Docker on `:6300`) | Bad — user runs Docker | None | Best (local) | Lace's default; ships persistent yellow warning banner |
| **In-browser WASM** | Best | +~20 MB | Best | 1am ships `midnight_ledger_wasm` (19 MB) + `midnight_onchain_runtime_wasm` (1.4 MB). MV3 service worker compatibility unverified |
| **Hosted proof service** | Best | None | Worst (sees plaintext) | 1am operates "Proof Station SDK" with `X-API-Key`; backend at `prove-and-submit` HTTP endpoint |

**You'll likely need at least two of these as a tiered fallback**, with the choice exposed to power users.

### 4. Send flow has two distinct types
Lace models this as `MidnightSpecificSendFlowType = 'send' | 'dust-designation'`. Dust-designation is its own first-class UX: no recipient, just "register these NIGHT UTXOs to generate DUST for this dust address." Two contextual notices in send sheet (privacy notice for shielded, designation warning for NIGHT-with-registrations).

### 5. Per-stream sync progress
The wallet has three independent sync streams (shielded / unshielded / dust). Sync ratio must be reported per stream:

```typescript
type MidnightWalletSyncProgress = {
  dust: Percent;
  shielded: Percent;
  unshielded: Percent;
  isStrictlyComplete: { dust: boolean; shielded: boolean; unshielded: boolean };
};
```

A single global percentage misleads the user.

### 6. DApp connector — separate spec from CIP-30
Same architectural pattern as CIP-30 but a different namespace and method set. Both Lace and 1am implement v4.0.1:

- Discovery: `window.midnight[walletId]` (frozen, non-writable property)
- 16 methods on `ConnectedAPI`: `getShieldedAddresses`, `getUnshieldedAddress`, `getDustAddress`, `getShieldedBalances`, `getUnshieldedBalances`, `getDustBalance`, `getTxHistory(page, size)`, `balanceUnsealedTransaction`, `balanceSealedTransaction`, `makeTransfer`, `makeIntent`, `signData`, `submitTransaction`, `getProvingProvider`, `getConfiguration`, `getConnectionStatus`, `hintUsage`
- 1am-only extras: `getTxHistory` is paginated, `ONEAM_SET_ICON` for dynamic icon
- Pin `apiVersion: '4.0.1'` to match `@midnight-ntwrk/dapp-connector-api`

This must coexist with Gero's existing CIP-30 (`window.cardano.gero`) — they share no surface.

### 7. SDK is WASM-heavy with bundler caveats
Foundation docs explicitly state: *"Packaging for web requires polyfills for Node's `Buffer` and `assert`."* Heavy packages:
- `@midnight-ntwrk/ledger-v8` — Rust→WASM ledger primitives (the big blob)
- `@midnight-ntwrk/wallet-sdk-node-client` — Polkadot API → loads WASM crypto
- The SDK assumes a Node-shim layer (matches Gero's existing Vite + nodePolyfills setup)

**Critical Lace gotcha**: their `midnight-context` (types/utils) package *cannot* import `ledger-v8` or it breaks both extension and mobile builds. Heavy SDK only goes in module-level packages. Gero should mirror this — keep `src/chains/midnight/` separable from `src/utils/` and `src/models/`.

### 8. No hardware wallet support is feasible (today)
Midnight ZK proof generation needs the secret key in cleartext at proof-gen time. Ledger/Trezor cannot expose private keys. **Lace explicitly ships in-memory only** — no `vault-ledger-midnight` package exists. Coin type `2400'` is also not on SLIP-0044 yet, so HW vendors don't derive it. Document the limitation; redirect HW users to the Glacier Drop portal flow.

### 9. DUST registration is a Cardano transaction
The mapping `CardanoAddress → DUSTAddress` is recorded on-chain via a Plutus validator on Cardano:
1. User builds a Cardano tx with output to the mapping validator + inline datum
2. Signs via existing CIP-30 (Gero already has this!)
3. Bridge relays mapping to Midnight node
4. Wait `~432 Midnight blocks (~2.5 hours)` for status to flip from Pending → Registered

This is inherently a multi-chain operation. Gero is uniquely well-positioned here because it already has Cardano signing.

# Backend Integration: Nexus

Nexus (`https://nexus.gerowallet.io`) is the multi-chain blockchain data REST API the wallet calls for chain reads. Spring Boot 3.5 / Java 21, with a sequential-fallback `ProviderOrchestrator` over Maestro / Koios / Blockfrost / yaci-store providers.

## Key insight: multi-chain is already a solved pattern

**Apex Prime and Apex Vector are already integrated**, and they did NOT get new controllers. They are served by the **same Cardano-shaped controllers** with a `?network=apex-prime-mainnet` query parameter. The chain dispatch happens inside `NetworkResolver` and the orchestrator filters providers by network.

This means routes are **chain-agnostic**: `/api/blocks/latest`, not `/api/v1/cardano/blocks/latest`. Adding Midnight follows the same pattern — for endpoints where Midnight maps 1:1 to Cardano concepts (blocks, transactions, addresses), **no new controllers or facades are needed**.

# Backend Integration: Gero-Sync

Gero-Sync is the WebSocket push-sync service. Spring Boot 3.5.4 / Java 21 / yaci-core (Cardano P2P). Wallet connects to `wss://<host>/ws/sync` with a JWT, sends `SUBSCRIBE`, and receives push notifications on every relevant block.

## Key insight: gero-sync is ALREADY multi-chain

The `ChainType` enum already has `CARDANO`, `BITCOIN`, `APEX_PRIME`, `APEX_VECTOR`. The WebSocket layer, `AddressRegistry`, `SyncDispatcher`, `CatchUpService` (mostly), and admin infrastructure are **fully chain-agnostic**. Bitcoin is integrated via a `BitcoinBlockPoller` (scheduled HTTP poller against Esplora) — and Bitcoin is the closer architectural template for Midnight than the yaci-based Cardano path, because Midnight needs HTTP/WS-based polling/subscribing (not native protocol).

## WS message protocol (already defined, applies to Midnight as-is)

**Inbound — `SUBSCRIBE`:**
```json
{
  "type": "SUBSCRIBE",
  "chain": "MIDNIGHT",
  "network": "midnight-mainnet",
  "address": "mn_addr_mainnet1...",   // unshielded address
  "lastSyncedBlock": 0,
  "credentials": ["..."],              // optional, address-derivation hashes
  "platform": "extension"
}
```

**Inbound — `SYNC_CHECK`:**
```json
{ "type": "SYNC_CHECK", "address": "mn_addr_...", "lastSyncedBlock": 12345 }
```

**Outbound — `SYNC` payload:**
```json
{
  "type": "SYNC",
  "chain": "MIDNIGHT",
  "network": "midnight-mainnet",
  "block": { "hash": "0x...", "height": 12346, "absoluteSlot": 0, "epochNo": 0, "timestamp": ... },
  "transactions": [{ "hash": "0x...", "cbor": "<hex tx body>", ... }],
  "account": { "controlledAmount": "...", "poolId": null, "drepId": null },
  "utxos": [...]
}
```

For Midnight: `absoluteSlot` and `epochNo` are zeroed (Substrate has no slot/epoch in the Cardano sense — could repurpose `epochNo` as session number later if useful). `cbor` field carries serialized Substrate tx hex (it's a plain `String`, not validated as CBOR). `poolId` / `drepId` are null. `controlledAmount` = unshielded NIGHT balance.

Worth tightening for Midnight if shielded address visibility is a privacy claim.

# Architectural reframing — push-driven, not pull-driven (2026-05-03)

**The original plan over-indexed on Cardano parity.** During Tier 1 implementation in Nexus, the agent discovered that Midnight's indexer schema is fundamentally different from a Cardano data API — and the original "every Cardano endpoint maps to a Midnight equivalent" framing is wrong.

## The actual indexer surface (verified live 2026-05-03)

The indexer schema has **26 queries and 6 subscriptions**. Crucially:
- **No `address` / `addresses` / `account` query.** Address-scoped data is **subscription-only**.
- **No top-level `blocks` (plural) query.** Only `block` (singular by hash/height); ranged block lists are subscription-only via `blocks`.

The indexer's design is: queries answer "what was X" for a specific known thing (a block, a tx hash, a contract). Subscriptions answer "what's happening to addresses I care about" — the wallet calls the `connect` mutation with its key material and receives `unshieldedTransactions` / `shieldedTransactions` / `dustLedgerEvents` / `zswapLedgerEvents` events over WS for those addresses.

This isn't an indexer limitation — it's the design. Foundation built it for SDK consumers who maintain their own state via subscription. Lace and 1am do exactly that: their wallets run the SDK, the SDK subscribes, the SDK builds local state.

## What this means for our service split

| Data type | Nexus role | Gero-Sync role |
|---|---|---|
| Block by hash/height | one-shot REST query (yes) | — |
| Transaction by hash | one-shot REST query (yes) | — |
| Tx submission | proxy POST to substrate RPC :9944 (yes) | — |
| Block range / recent blocks list | **NOT BUILDABLE as REST** — only available via `blocks` subscription | gero-sync maintains a tip cache; expose via WS event |
| Address balance / UTxOs / tx history | **NOT BUILDABLE as one-shot REST** — push-only | **gero-sync owns this.** Subscribes on behalf of clients, maintains per-session state, pushes via existing `SyncPayload` envelope |
| DUST generation status | one-shot REST query (yes, via `dustGenerationStatus` query) | optional: also push live via `dustLedgerEvents` subscription |
| Contract state | one-shot REST query (yes, via `contractAction` query) | optional: live via `contractActions` subscription |
| SPO / pool / epoch / governance | one-shot REST queries (yes, 22 query fields) | — |
| Tx UTxO inputs/outputs | one-shot REST query (yes) — but in **Midnight-shaped DTO**, not coerced to Cardano's `TxIO` | — |

## Concrete consequences

1. **Drop `MidnightAddressServiceImpl` entirely** — don't ship a Cardano-shaped REST endpoint that returns "not supported." The wallet for Midnight talks to gero-sync's WS for address state, not to Nexus's `/api/addresses/*`. Tell future implementers explicitly so they don't try to "fix" it.

2. **Drop the multi-block listing endpoint** — same reason. `getBlocks(page, pageSize)` is a Cardano concept. For Midnight, the wallet uses live tip + walks back via `block(by=parentHash)` if it ever needs history (rarely).

3. **Promote Tier 2 (GraphQL/WS proxy) to Tier 1.5.** Originally Tier 2; now effectively required. Reasoning: if the wallet uses the SDK directly for address state (the Lace/1am pattern), the SDK needs an indexer URL — and that URL should be Nexus's proxy (for auth, rate limit, observability), not the public Foundation indexer.

4. **UTxO DTOs are Midnight-shaped, not Cardano-shaped.** A `MidnightUnshieldedTxIODto` carries `tokenType` (UUID-ish), `intentHash`, `outputIndex`, etc. Don't try to populate a Cardano `TxIO` — the wallet has to know it's Midnight anyway (different signing path).

5. **Pool/Epoch/Governance services on Midnight are buildable but currently return placeholder data** — `APP__INFRA__SPO_NODE__BLOCKFROST_ID: placeholder` is set in the deployed indexer. Provisioning a real Blockfrost ID is a prerequisite to those endpoints returning useful data. **Defer until Blockfrost ID is live, or scope SPO out of v1.**

6. **Gero-Sync's responsibility expands.** It's no longer just "real-time updates on top of REST" — for Midnight specifically, it's the **only** path to address-scoped data. The catch-up flow on `SUBSCRIBE` must fully reconstruct address state from indexer subscriptions (not from a Nexus REST query, because none exists). See updated gero-sync handoff doc for the new responsibility map.
