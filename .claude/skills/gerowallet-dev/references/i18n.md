# i18n and UI copy

vue-i18n 8.28.2, two production locales: `us` (English, eagerly bundled) and `de` (German, lazy-loaded). Each is a **flat map of literal dotted keys**, ~4935 keys per file.

```ts
'governance.status.active': 'Active',
```

Not a nested object tree. This works only because vue-i18n tries path traversal first and falls back to a direct `message[key]` lookup. **Never nest** - a nested block silently shadows or collides with the flat map.

## Nothing checks your work. Nothing.

Verified by executing the repo's own vue-i18n:

| Situation | What the user sees | What warns you |
|---|---|---|
| Key in `us.ts`, missing from `de.ts` | The English string | Nothing. `fallbackLocale: 'us'`, and `silentFallbackWarn` is on |
| Key missing from both | The raw key text, e.g. `governance.status.foo` | Nothing. `silentTranslationWarn` is on |
| Hardcoded English string, no `$t()` | Untranslatable text | Nothing |

There is no repo-wide parity spec, no npm script, no CI job and no ESLint rule. One namespace is the exception: `src/services/copilot/noAdvice.spec.ts` asserts full EN/DE key parity for `copilot.onboarding.*`, `copilot.vibe.*`, `copilot.category.*` and `copilot.settings.*`, and that every `copilot.feed.*` narration key is non-empty in both. Nothing covers any other namespace, and that spec is not in a required check's path list. The tree already carries drift.

**So treat parity as a manual step you owe the user.** After adding a key:

```bash
grep -n "'my.new.key'" src/plugins/i18n/us.ts src/plugins/i18n/de.ts   # must print exactly 2 lines
```

## Search before you mint

430 distinct English strings are already duplicated across 1225 keys. "Insufficient balance" alone exists many times over.

```bash
grep -n -i -F "insufficient balance" src/plugins/i18n/us.ts     # search by VALUE first
grep -n "^  'errors\." src/plugins/i18n/us.ts                   # list a namespace
```

`common.*` (200 keys) and `errors.*` (15 keys) hold the shared copy. Look there first.

**Namespaces are not contiguous.** `errors.*` appears at `us.ts:2775-2786` and again at `3715-3719`, interleaved with other blocks. Grepping one block and appending to it creates a duplicate. Grep the whole file for the prefix.

## Adding a key

Append at the **end of both files**, in the same order in both. Do not try to match line numbers: key order between the two files matches only 14% of the time, and diverges from index 42 onward. Locate an existing German slot by key name, never by position.

Prefer the **key** over German text when searching `de.ts`. Most of the file is literal UTF-8 (`grep -c "für"` returns 151), but one block near the top (`de.ts:21-46`, 10 lines) stores umlauts as `\uXXXX` escapes, so a value there will not match a grep for `löschen`.

## Using translations

| Where | How |
|---|---|
| Template | `$t('key')` directly (3114 uses) |
| `<script setup>` | `const { t } = useTranslation()` from `@/shared/composables/useTranslation` (397 uses). There is no `this` |
| Plain `.ts` module | `import i18n from '@/plugins/i18n'` then `i18n.t('key') as string` |

`this.$t(` appears zero times in the repo. Interpolation is named with single braces: `'{count} of {total} wallets'`, params passed as a second object argument.

## Do not delete a key just because grep finds no caller

Keys are composed at runtime from template literals. Live dynamic prefixes include `governance.status.${...}`, `governance.${...}`, `vaults.status.${vault.status}`, `signTx.risk.${riskBadge.label}`. Check with:

```bash
grep -rnE "t\(\`|\\\$t\(\`" src --include="*.vue" --include="*.ts"
```

The house convention is to keep a superseded key as a **tombstone with a comment** rather than delete it - deleting an i18n key is riskier than leaving it.

`StatusPill.vue` is the reference implementation of the defensive pattern for runtime-composed keys.

## Copy rules

- **No em dashes in user-facing strings.** Zero appear in any translation value in either file; a deliberate sweep removed them. Use a period, colon, comma or parentheses; use the middle dot `·` only to separate two values on one line. Em dashes are fine in code comments and commit messages.
- **German uses an en dash `–` where English uses a plain hyphen `-`.** `de.ts` keeps 11 of these deliberately (numeric ranges and the Gedankenstrich). Never `—` in either file.
- **Sentence case.** This is the live convention (the newest namespaces are 0-15% Title Case) and matches the design system, which forces `text-transform: none` on every button. Older namespaces (assets, swap, perpetuals, transactions, cashback) are 86-92% Title Case - **do not** match your neighbours there.
- **Error messages are full sentences ending in a period**; short label-style errors have none. The recovery clause is `Please try again.` or a specific instruction.
- **Changing an English value means changing the German one too.** Several specs assert against the real i18n singleton, so a reworded string can also break tests.

## Adding a locale

Needs three things, not one: the `<lang>.ts` file, an entry in `READY_LANGUAGES` (`src/plugins/i18n/config.ts`), and the Vuetify locale in the `vuetifyLocales` map. `src/plugins/languages.ts` lists 22 languages, but only the two in `READY_LANGUAGES` exist. A locale set with no file is silently aliased to English.
