# Solana

Solana support, gated by the `isSolanaEnabled` feature flag (default off).

This folder is the chain core. Wallet create/restore, Gero Sync and the screens (balance, tokens, activity, receive, send) are wired in. The side panel shows no Solana view yet.

## Wiring

- **Wallet record** (`gero-db.ts`): `publicKey` is account #0's base58 address and the stored root key is the 64-byte BIP-39 seed, so added accounts (`softwareAccounts`, `addAccountKeys`) derive from it. Wallet identity compares addresses exactly (`walletIdentity.ts`).
- **Networks** (`utils/networks.ts`): Solana Mainnet (`comingSoon`) and Devnet, every feature off. `NetworkSelector` shows no Solana tile while `isSolanaEnabled` is off.
- **Gero Sync**:
  - `walletManager` subscribes `chain: 'SOLANA'` by the record's address, with the slot cursor from the wallet's `sync` table.
  - `websocket.service` sends the Solana SUBSCRIBE. On a catch-up it keeps the cursor at the newest delivered slot, and carries the `solana_*` snapshot through.
  - `sync.service.applySolanaSync` merges into `walletStore.solanaTransactions` (IndexedDB bulk field) and `walletStore.solana` (balance, tokens, tip slot), and persists the cursor.
  - `FORCE_RESYNC` clears both and re-subscribes at 0.
- **Screens**: `PortfolioPage` renders `SolanaDashboard.vue` (balance, SPL tokens by mint, the latest 25 transactions with Solscan links). Receive is the shared `ReceiveDialog` (one address, its path). Send is `SolanaSendDialog.vue`, opened from the quick actions.
- **Send** (`chrome/solanaSend.ts`, extension pages only):
  - `SOLANA_SEND_QUOTE` gives the fee at two levels: Standard (median priority price) and Fast (p75), from Nexus `/api/sol/fees`, capped at `MAX_PRIORITY_MICRO_LAMPORTS`.
  - `SEND_SOLANA` takes only the recipient, lamports and fee level. The worker reads the sender, balance and price itself and applies `checkSolTransfer` (`solanaSendRules.ts`, the same rules the dialog shows): a valid address that is not the wallet's own, a known balance, the fee counted, no leftover below the rent-exempt minimum, and no new recipient account opened below it.
  - It then takes a recent blockhash from Nexus `chain/tip`, signs in `WalletBg.signSolanaTransfer` (phrase → key at the record's account, refused unless it gives the record's address, wiped after) and submits through Nexus.
  - Pages see an error code only (`solanaSendErrorKey`), never server text. `SUBMIT_FAILED` tells the user to check their activity before retrying, because the transaction may have landed.
- **dApp connection** (behind `isSolanaEnabled`; the worker reads it from the flag mirror):
  - `chrome/injectSolana.ts` registers Gero as a Wallet Standard wallet (never `window.solana`) once `SOLANA_METHOD.available` says the flag is on: `standard:connect` / `disconnect` / `events`, `solana:signIn`, `solana:signMessage`, `solana:signTransaction` and `solana:signAndSendTransaction`.
  - `SOLANA_METHOD.connect` answers a connected site with the account at once, never prompts a `silent` call, and otherwise parks a side-panel prompt (with the account picker) as Midnight's connect does. Connections are the account's own `connected_dapps` rows.
  - `SOLANA_METHOD.signMessage` is for a connected site and the connected account only. `solanaSignMessage.ts` refuses empty, oversized and transaction-shaped bytes (a signature over a transaction message signs that transaction) in the handler, in the panel's `SIGN_SOLANA_MESSAGE` and in `WalletBg.signSolanaMessage`. The worker checks the panel's signature against the account's key and the exact bytes before the dApp gets it.
  - **Account switches**: `walletStore.setLoggedWallet` sends every tab `SOLANA_ACCOUNT_SIGNAL` when the logged account changes. It carries nothing, so the content relay passes it without the whitelist check. A page that is connected re-reads its account with a silent `solana_connect` (never a prompt; it answers only a site connected to the new account) and emits Wallet Standard `change`: the new account, or no accounts. A page the dApp disconnected, or never connected, does nothing.
  - **Sign in with Solana** (`SOLANA_METHOD.signIn`, `solanaSignIn.ts`): the worker checks the dApp's fields (the domain is the requesting site's host, the address the logged account, the chain the wallet's network, no field contains a line break, not expired or not yet valid) and builds the SIWS text exactly as `@solana/wallet-standard-util`'s `createSignInMessageText`, filling in only the domain and address (dApps verify every other field against their own input). The side panel shows that text and signs it as a message (`SIGN_SOLANA_MESSAGE`); the worker verifies the signature and, for a site not connected yet, connects it with the logged account.
  - **Transactions** (`SOLANA_METHOD.signTransaction` / `signAndSendTransaction`, one handler, `chrome/solanaDappTx.ts`): a connected site and account only, on the wallet's chain. The worker decodes the bytes itself (`solanaTxWire.ts`: legacy and v0, strict), refuses one the account does not sign, resolves lookup tables through Nexus `POST /api/sol/accounts`, reads the instructions (`solanaTxInstructions.ts`: transfers, fee, and what hands over control: Assign, SetAuthority, Approve, CloseAccount to someone else, nonce authority, durable nonce) and simulates through Nexus `POST /api/sol/txs/simulate` with the wallet and every writable account (at most 32). `solanaTxPreview.ts` compares those accounts before and after: the wallet's SOL and token changes, and a token account or the wallet changing owner or gaining a delegate inside a program (CPI). The side panel shows it; a critical warning must be acknowledged before signing.
  - The transaction is signed exactly as the dApp sent it: no blockhash, fee or instruction is swapped in. Preparing grants an allowance for that message that lasts while its prompt is open (`chrome/solanaTxAllowance.ts`, at most 10 min, counted per prompt); the panel's `SIGN_SOLANA_TRANSACTION` checks it before any secret is opened (a wrong password can be retried: an ed25519 signature is deterministic, so signing again gives nothing more away), and `WalletBg.signSolanaDappTransaction` signs nothing else. The worker accepts the panel's result only if nothing but the wallet's signature slot changed and that signature verifies (`isSignedByWalletOnly`). `signAndSend` then submits through Nexus with preflight; a submit with no answer is reported as unconfirmed, never as "nothing was sent".
  - Errors reach the page as Errors with Phantom's codes (`solanaDappProtocol.ts`: 4001 declined, 4100 not connected, 4200 unsupported).
- **Token send** (`chrome/solanaTokenSend.ts`, `solanaTokenTransfer.ts`): the page names the mint, recipient, raw amount and fee level only. The worker takes the source token account from its own Gero Sync holdings and has Nexus confirm it (the wallet's, that mint, not frozen, enough balance); reads the mint (Token or Token-2022, decimals; non-transferable, transfer-hook and paused mints are refused); accepts a recipient that is a wallet (on-curve, unused or a System account) or a token account of that mint; builds `TransferChecked`, with `CreateIdempotent` first when the recipient has no associated account (the sender pays its rent); and simulates the exact message, which must succeed and show the amount leaving the source and arriving, less any Token-2022 fee. `SOLANA_TOKEN_SEND_QUOTE` gives the review those figures; `SEND_SOLANA_TOKEN` plans again, signs and submits; hardware wallets use `PREPARE_SOLANA_SEND` with a `mint`.
- **NFTs** (`solanaNfts.ts`): held tokens with 0 decimals and one unit are candidates; `sync.service.syncSolanaNfts` asks Nexus `POST /api/sol/nfts/metadata` about the mints it does not know (Metaplex metadata or a Token-2022 metadata extension, plus the off-chain JSON, read through Nexus's SSRF-guarded fetcher) and keeps them in `walletStore.solanaNfts` (a bulk field). The wallet re-checks every row (mint, URL schemes, string lengths). Only a VERIFIED collection groups NFTs; an unverified one stands alone with a warning. Text is shown as text and images go through Gero's image proxy (`assets.resolveIcon`). An NFT is sent with the token send (`SolanaSendDialog` `nftMint`: asset and amount fixed). A programmable NFT (frozen by Token Metadata) goes through Token Metadata `TransferV1` (`solanaPnftTransfer.ts`): the planner asks Nexus for its standard and rule set, sends only from the owner's associated account to a wallet's, names both token records and the rule set, and the simulation must show exactly the one NFT moving; the review shows the deposits the program takes and the token record rent it returns. Compressed and Metaplex Core NFTs are not token accounts and are not shown.
- **Compressed and Core NFTs** (`solanaAssets.ts`, `solanaAssetTransfer.ts`, `chrome/solanaAssetSend.ts`): not token accounts, so Nexus lists them from a DAS index (Helius: `GET /api/sol/addresses/{a}/assets`, kept in `walletStore.solanaAssets` by `sync.service.syncSolanaAssets`, read again when anything moves) and they join the collectibles. A send uses the same quote and send messages as tokens; the worker routes an asset IT lists for the account to the asset planner, reads `GET /api/sol/assets/{id}/transfer` fresh (owner must be the account, not frozen; a compressed NFT must be in a V1 Bubblegum tree and goes with the current root and the canopy-trimmed proof; a Core asset passes its collection), accepts only a wallet recipient, and simulates the exact message, which may cost the sender at most the fee. Without a DAS URL in Nexus they are simply not listed.
- **Native staking** (`solanaStaking.ts`, `solanaStakeTransfer.ts`, `chrome/solanaStake.ts`, the dashboard's `SolanaStakingCard`):
  - The card reads Nexus `GET /api/sol/addresses/{a}/stakes`, `/api/sol/validators` and `/api/sol/stake/info` (`useSolanaStaking`), read strictly: a stake row must name the account in the role it claims. Validator names, links and details are what each validator published about itself: shown as text next to the vote account, never as verified, and links only for https.
  - **Stake** creates the first unused `stake:N` account derived from the wallet (`CreateAccountWithSeed`, so the wallet is the only signer and hardware wallets sign it like a transfer), initializes it with the wallet as staker and withdrawer and no lockup, and delegates it. **Unstake** is `Deactivate`; **Withdraw** takes everything withdrawable back to the wallet.
  - The page sends the action, the vote account and amount or the stake account, and a fee level (`SOLANA_STAKE_QUOTE`, `SOLANA_STAKE`; hardware: `PREPARE_SOLANA_STAKE`, then the send's `SUBMIT_SOLANA_SEND`). The worker reads the validator list, the minimum delegation, the reserve, the account's stake accounts and the chain again, keeps `STAKE_KEEP_LAMPORTS` in the wallet for later fees, refuses a delinquent or unlisted validator, and simulates the exact message: a stake must fund a Stake-program account with exactly the stake plus its reserve, an unstake may cost the fee only, a withdrawal must pay the wallet the amount less the fee. The page passes the reviewed limits back (`maxSolCost`, `minReceived`).
- **Hardware wallets** (`solanaHardwarePolicy.ts`): Ledger, Trezor and Keystone pair at the same path as software wallets, with the multi-account picker. They sign in the page (`src/shared/utils/solanaLedger.ts`, `trezor.ts` `getSolanaAccounts`/`signSolanaTransaction`, `solanaKeystone.ts`; `useSolanaHardwareSigner`) and the worker checks every signature: Gero's Send is `PREPARE_SOLANA_SEND` (the worker checks the transfer, builds the message and holds it for that account, 5 min) then `SUBMIT_SOLANA_SEND` (only a 64-byte signature, verified against the account over that exact message before the worker assembles and submits it). A dApp transaction is signed on the device and put in the wallet's slot by the panel; `isSignedByWalletOnly` checks it as for a software wallet. Ledger and Trezor sign messages only in Solana's off-chain format, which dApps reject, so only Keystone signs `signMessage` and Sign in with Solana (`solanaHardwareSignsMessages`).
- Imports of this folder from code in the background bundle are static, never `await import()`: an inlined dynamic-import namespace can be read before it is declared (`scripts/check-bundle-tdz.mjs`).

`src/api/solana-api.ts` is the Nexus `/api/sol` client. It calls Nexus directly with the device JWT, as the Midnight client does; device tokens carry `SOLANA_READ`/`SOLANA_WRITE`. Realtime updates come from Gero Sync, and this client covers on-demand reads, fees and submit.

## Rules

- Never persist or log a `secretKey`. Derive it from the phrase when signing, then wipe it.
- An unknown balance is `undefined`, never `0`. Gero Sync omits a field when Nexus failed.
- The Gero Sync cursor (`lastSyncedBlock`) is a slot. Only a `SYNC` that delivered transactions moves it; the `block` on `CATCH_UP_COMPLETE` / `SYNC_CHECK_OK` is the tip, for display.
- Networks are `Mainnet` and `Devnet` (Nexus `solana-mainnet` / `solana-devnet`). Gero Sync and Nexus serve no others.

## Tests

`npx vitest run src/chains/solana` runs the unit tests. The key derivation is pinned to `solana-keygen` output.

`solanaTransaction.localnet.spec.ts` submits real transfers to a validator and checks the fee and balances. It is skipped unless you point it at one:

```bash
solana-test-validator --reset
VITE_SOLANA_LOCALNET_RPC=http://127.0.0.1:8899 npx vitest run src/chains/solana/solanaTransaction.localnet.spec.ts
```
