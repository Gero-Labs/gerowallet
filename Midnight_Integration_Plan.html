Midnight Blockchain Integration Plan

Gero Wallet - Technical Architecture & Implementation Roadmap

Based on Lace Wallet Codebase Analysis

Date: December 11, 2024

TL;DR - Critical Findings
  • Three-Wallet Architecture: Midnight requires managing 3 separate wallet instances simultaneously (DustWallet, ShieldedWallet, UnshieldedWallet) - fundamentally different from Cardano's single-wallet model
  • Three Keys Per Account: Each account needs 3 separate derived keys (Zswap, Dust, NightExternal) vs. Cardano's single spending key
  • Explicit DUST Registration: Users must manually register NIGHT UTXOs to generate DUST - not automatic like staking rewards
  • Massive Fee Overhead: Additional fee overhead of 300 trillion (3×10¹⁴) - significantly higher than Cardano
  • Timeline: 15-18 weeks for full implementation with 6 distinct phases

1. Executive Overview

Following comprehensive analysis of the Lace Wallet Midnight Preview RC 251202 codebase, we've identified critical architectural differences between Midnight and Cardano that significantly impact our integration approach. Unlike Cardano, Midnight requires a three-wallet architecture managing separate instances for DUST generation, shielded transactions, and unshielded operations.

2. Critical Architecture Changes

🔴 Change #1: Three-Wallet System

Original Assumption: Single wallet managing NIGHT + DUST tokens

Lace Reality: Three separate wallet instances working in coordination

interface MidnightWalletSystem {
  dustWallet: DustWallet;           // DUST generation & unshielded operations
  shieldedWallet: ShieldedWallet;   // Private NIGHT (zswap/zkProofs)
  unshieldedWallet: UnshieldedWallet; // Public NIGHT transactions
  walletFacade: WalletFacade;       // Unified interface to all three
}

Impact: Cannot reuse existing Cardano wallet patterns. Requires complete refactor of wallet initialization, state management, and transaction orchestration.

🔴 Change #2: Three Key Derivation Paths

Original Assumption: Single derivation path m/44'/2400'/account'/role/index

Lace Reality: Three separate keys with specific role assignments

// THREE keys derived from same seed (not one)
const zswapKey = derive(seed, [44, 2400, account, 3, 0]);      // Role 3 = Zswap
const dustKey = derive(seed, [44, 2400, account, 2, 0]);       // Role 2 = Dust
const nightExternalKey = derive(seed, [44, 2400, account, 0, 0]); // Role 0 = NightExternal

// All three encrypted separately with EMIP3
const encryptedKeys = {
  zswap: emip3encrypt(zswapKey, password),
  dust: emip3encrypt(dustKey, password),
  nightExternal: emip3encrypt(nightExternalKey, password)
};

Impact: Key management complexity triples. Need to store/encrypt three keys instead of one. Wallet recovery must restore all three keys.

🔴 Change #3: Explicit DUST Registration

Original Assumption: DUST generates automatically from NIGHT holdings

Lace Reality: Users must explicitly register each NIGHT UTXO for DUST generation

// Coins have registration flag (not automatic)
interface UnshieldedCoin {
  value: bigint;
  type: TokenType;
  registeredForDustGeneration: boolean;  // ⚠️ Requires user action
  ownerAddress: string;
}

// Manual registration required
await wallet.registerNightUtxosForDustGeneration(
  selectedUtxos,
  dustAddress
);

Impact: Requires dedicated registration UI with coin selection. Cannot assume all NIGHT generates DUST. UX flow similar to staking pool delegation.

🔴 Change #4: Five Balance Components

Original Assumption: Two balances (NIGHT + DUST)

Lace Reality: Five distinct balance components

interface MidnightBalances {
  // NIGHT balances
  nightShielded: bigint;        // Private NIGHT (zswap)
  nightUnshielded: bigint;      // Public NIGHT
  nightRegistered: bigint;      // NIGHT registered for DUST (subset of unshielded)

  // DUST balances
  dust: bigint;                 // Current DUST balance
  dustGenerating: bigint;       // DUST being generated (not yet claimed)
}

Impact: Dashboard needs granular balance display. Cannot simply show "NIGHT balance" - must differentiate public/private/registered.

🔴 Change #5: Massive Fee Overhead

Original Assumption: Standard Cardano-like fee calculation

Lace Reality: 300 trillion (3×10¹⁴) additional fee overhead

costParameters: {
  additionalFeeOverhead: 300000000000000n,  // 300 TRILLION
  feeBlocksMargin: 5
}

Impact: Fee estimates will be significantly higher than Cardano. Requires prominent fee warnings in UI to manage user expectations.

4. Implementation Roadmap

Phase 1: Three-Key Foundation (2 weeks)

Deliverables:

  • Implement deriveThreeKeys() utility with BIP32 derivation for roles 0, 2, 3
  • EMIP3 encryption for all three keys (reuse Gero's existing crypto utilities)
  • IndexedDB schema extension for three encrypted keys per Midnight account
  • Generate three addresses from three wallet instances

Risk: LOW - Leverages existing Cardano crypto patterns

Phase 2: Three-Wallet Initialization (2 weeks)

Deliverables:

  • Initialize DustWallet, ShieldedWallet, UnshieldedWallet from SDK factories
  • WalletFacade integration for unified transaction API
  • State serialization/restoration for fast wallet recovery
  • GraphQL client setup with Apollo Client + WebSocket subscriptions

Risk: HIGH - New architecture pattern for Gero

Phase 3: Five-Balance Dashboard (2 weeks)

Deliverables:

  • Dashboard UI displaying all 5 balance components with visual differentiation
  • Three-address display component with type selector
  • QR code generation for all three address types (dust/shielded/unshielded)
  • Copy-to-clipboard with address type labels

Risk: MEDIUM - Complex UX but proven in Lace

Phase 4: DUST Registration Flow (3 weeks)

Deliverables:

  • Coin selection UI showing all unshielded NIGHT UTXOs with registration status
  • Registration toggle per UTXO with confirmation dialog
  • registerNightUtxosForDustGeneration() SDK integration
  • deregisterFromDustGeneration() SDK integration
  • Real-time DUST generation progress display (current/max, time remaining)

Risk: MEDIUM - Novel UX pattern for crypto wallets

Phase 5: Transaction System (4 weeks)

Deliverables:

  • Unshielded NIGHT transfers (simple, fast, public)
  • Shielded NIGHT transfers (requires ZK proofs, 10-15 second operation)
  • DUST transfers (unshielded only)
  • Proof server client with progress UI ("Preparing → Proving → Submitting")
  • Fee calculation with massive overhead (300 trillion) and user warnings

Risk: HIGH - ZK proof UX critical for user retention

Phase 6: GraphQL Sync & Real-time Updates (2 weeks)

Deliverables:

  • WebSocket subscription to dustLedgerEvents for DUST balance updates
  • WebSocket subscription to zswapLedgerEvents for shielded NIGHT updates
  • Real-time balance updates across all 5 components
  • Transaction confirmation notifications
  • Reconnection logic for dropped WebSocket connections

Risk: MEDIUM - WebSocket stability crucial

Phase 11: Cardano Bridge for DUST Generation (Optional - Post-MVP)

Deliverables:

  • CIP-30 Cardano wallet connection (Nami, Eternl, Lace)
  • Address mapping UI (Cardano ↔ Midnight DUST address)
  • Plutus validator integration for on-chain mapping
  • Cross-chain DUST generation from Cardano NIGHT holdings
  • Unified balance display (Cardano NIGHT + Midnight DUST)

Risk: MEDIUM - Cross-chain complexity

7. Risk Assessment & Mitigation

High Risk Items

🔴 Three-Wallet Coordination Complexity

Risk: Managing three wallet instances simultaneously is unprecedented in Gero. High risk of state desynchronization between wallets.

Mitigation:

  • Implement comprehensive state serialization (following Lace's pattern)
  • Use WalletFacade as single source of truth for transaction orchestration
  • Add extensive logging for wallet state transitions
  • Build debug panel showing all three wallet states simultaneously

🔴 ZK Proof Generation UX (10-15 seconds)

Risk: Users may abandon transactions thinking the app has frozen during proof generation.

Mitigation:

  • Implement multi-stage progress indicator ("Preparing → Proving → Submitting")
  • Show estimated time remaining with countdown timer
  • Allow users to minimize transaction dialog while proof generates
  • Add educational tooltips explaining why privacy requires time

🔴 Massive Fee Overhead User Shock

Risk: 300 trillion additional fee overhead may shock users accustomed to low Cardano fees.

Mitigation:

  • Prominent fee warnings in transaction dialogs
  • Fee breakdown showing base fee vs. overhead
  • Educational content explaining Midnight's cost model
  • Fee simulation before actual transaction submission

Medium Risk Items

⚠️ GraphQL WebSocket Subscription Stability

Risk: WebSocket connections can drop, causing missed balance updates.

Mitigation:

  • Implement exponential backoff reconnection logic
  • Offline mode with cached state and sync-on-reconnect
  • Visual indicator for connection status in UI
  • Fallback to HTTP polling if WebSocket fails repeatedly

⚠️ DUST Registration UX Complexity

Risk: Users may not understand explicit DUST registration requirement.

Mitigation:

  • Onboarding wizard explaining DUST generation mechanics
  • Clear visual indicators for registered vs. unregistered NIGHT
  • Tooltips and help icons throughout registration flow
  • Suggested UTXO registration based on DUST generation potential

Low Risk Items

✅ EMIP3 Encryption Compatibility

Benefit: Midnight uses same EMIP3 encryption as Cardano - can reuse Gero's existing crypto utilities.

Advantage: No new encryption infrastructure needed. Proven security model.

✅ Lace's Proven Architecture

Benefit: Lace has production deployment with Midnight Preview - architectural risks are validated.

Advantage: Can reference Lace's solutions for edge cases and optimization patterns.

10. Key Takeaways for Leadership

✅ Good News

  • EMIP3 Encryption Reuse: Midnight uses same encryption as Cardano - can leverage existing Gero crypto utilities
  • Proven Architecture: Lace's production deployment validates the three-wallet approach - reduces architectural risk
  • State Serialization: Wallet state serialization enables fast recovery and reduces sync times
  • Clear Roadmap: 6 well-defined phases with measurable deliverables

⚠️ Challenges

  • Paradigm Shift: Three-wallet architecture is fundamentally different from Cardano - cannot simply "add Midnight like Apex Fusion"
  • UX Complexity: DUST registration is not automatic (unlike staking rewards) - requires user education
  • Fee Overhead: Massive additional fees (300 trillion overhead) require prominent user warnings to manage expectations
  • ZK Proof Delays: 10-15 second proof generation is SDK limitation - must design UX around this constraint
Bottom Line Recommendation

Midnight integration is technically feasible within 15-18 weeks with 2-3 engineers, but requires significant architectural changes to Gero's wallet infrastructure. The three-wallet system introduces complexity beyond typical multi-chain support.

Recommended Approach:

  1. Start with Phase 1-2 (4 weeks) as proof-of-concept to validate three-wallet architecture in Gero's codebase
  2. Conduct user research on DUST registration UX during Phase 2-3 (critical for adoption)
  3. Make go/no-go decision after Phase 2 based on architectural integration complexity
  4. If proceeding, allocate 2 engineers for parallel Phase 4-5 execution to meet 15-week timeline

Alternative: Consider MVP with unshielded NIGHT only (skip shielded wallet) to reduce initial scope by ~30%, then add privacy features in Phase 2.
